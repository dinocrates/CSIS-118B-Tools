Structure layout explorer

Choose field widths and explicit padding. Derive offsets, instance stride and little-endian bytes.

This bounded teaching model does not execute NASM or access real memory. The layout definition names offsets; the two simulated instances hold separate initialized bytes. NASM struc does not automatically align fields. Padding here is explicit, including any trailing padding you choose.

1. Define a layout and two instances

Values accept decimal integers or nonnegative hexadecimal. Each numeric field accepts its signed minimum through unsigned maximum. “8 inline bytes” uses a bit pattern to initialize bytes, not a stored pointer or an automatic string. Padding is zero-filled in these simulated instances.

Explain the result

Field address = base + instance index × structure size + field offset. An access is valid in this model only when the field and instance exist and every byte fits the unsigned 64-bit address range. Real programs must also have valid allocated storage.

The P101 preset has tag at 0, three explicit padding bytes, signed DWORD value at 4, and eight inline name bytes at 8: size 16. Removing padding gives value at 1, name bytes at 5 and size 13. No automatic padding is inserted. A relative field offset does not establish the base address’s alignment.

A byte array is not a pointer. The preset's “north” and “south” patterns include zeros in their eight-byte fields. Editing the pattern can remove every terminator; this tool displays that fact but never calls a string-printing helper. Numeric interpretation of an inline byte array is only a view of its bits.

Use a named offset such as [r12+Gauge.value] to load a field, with the matching width. Use lea rdi,[r12+Gauge.name] to form the inline bytes’ address. These are partial address examples, not standalone programs; P101 provides complete aligned callers. This explorer does not model procedure execution or macro expansion.
