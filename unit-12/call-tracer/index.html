Where does RET go?

Follow return addresses, stack alignment and a saved register through one small program.

This fixed teaching simulation executes no machine code and accesses no memory. Stack addresses are illustrative; return addresses are symbolic line numbers. It follows the verified course startup’s CALL main: main enters with RSP modulo 16 = 8. Actual helper internals are abstracted, and no exact volatile-register value is promised.

1. Choose a trace

Changing either choice resets the trace. The stack grows toward lower addresses. CALL pushes 8 bytes; RET pops 8 bytes. The caller aligns RSP to 16 bytes before CALL, so the callee enters at remainder 8.

      Explain the contract
      Leaf square makes no calls, so it needs no alignment adjustment. Non-leaf report reserves and removes eight bytes around its helper call. Main’s push r12 both saves the incoming value and provides its alignment; adding another eight bytes there would misalign its calls.
      RAX and RDI are caller-saved; a caller must not assume they survive a helper. R12 is callee-saved: a procedure that changes it must restore its incoming value before returning. Here main temporarily holds the square in R12 and restores the original 1234 sentinel. The abstract helper marks RAX unspecified to teach the contract, not to predict its actual implementation.
      Padding is not a return address. Remove padding before RET so the top slot is the saved return address. The counterexample stops at an ABI check; this is a teaching guard, not a claim that CALL itself always faults on misalignment. The course exit macro terminates execution; it does not return to the instruction after it. This trace instead returns from main to startup, which terminates.
      System V AMD64 calling convention: official psABI source. Stack arguments, local frames and the full register convention belong to the next unit.
